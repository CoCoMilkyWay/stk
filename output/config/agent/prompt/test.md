# 工具自检

这一段会话不挖因子, 是**工具自检**: 把 "工具" 节里的每个工具都调一遍 ({{tools}}), 确认它们按说明工作. 成绩好坏无所谓; 候选与全局记录落在测试目录, submit_factor 只查门槛, 不会拷进正式库.

## 节奏
- 分几轮做完, 每批至多 {{max_calls}} 个调用, 互不依赖的放进同一批; 要用上一步结果的 (候选名、代码、日期、研报 id、续读位置) 放到下一批.
- {{ask}}.

## 主路径: 按序做
1. **回测**: 交 3 个 eval_factor: 一个简单模板 (正式库有本持有期的因子就改写其一) / 一个只把它的截面根 CsRank 换成 CsNormRank 的 (应报同式不落) / 一个算子超上限的 (应拒收).
2. **喂观察**: 落了权重的候选拿去喂每个观察工具的 factor, 再 submit_factor 它.
3. **全局记录**: request_feature / request_tool / note_insight / report_issue 各提一条 (标题以 "[自检]" 开头, 内容照实写这次自检里看到的), 再用 ref 附议其中一条; 提完用 list_notes 查回来.

## 退回: 每类故意写错一个, 看原因是否说清、同批其余调用是否照做
不存在的候选 / 叶 / 代码 / 研报 id, 评估期外的日期, 超长的 rows, 不存在的 ref.

## 核对与收尾
- **核对**: 每个结果对照工具说明查 —— 该有的部分齐不齐、数是否合理 (分位 0..100、mono ∈ [-1, 1]、量级不离谱、计数自洽)、续读接不接得上、出错原因是否说清. 发现问题即 report_issue (type bug), detail 写明 工具 + 参数 + 看到了什么 + 预期是什么.
- **收尾**: report_issue 写一条总评 (type idea; 每个工具一行: 正常 / 有问题及哪一条的编号), 再 finish.
